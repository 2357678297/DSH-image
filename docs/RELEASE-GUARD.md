# 维护者更新编辑器

这是源码仓库的本地 Windows 工具，不是工作台左下角「更新」按钮。**用户按钮继续只做检查与拉取；编辑器不提供 HTTP 服务，不注册 agent 工具，也不会定时发布、生成图片或重启 DSH。** 适用于有仓库维护权限、已配置 Git 和 Node.js 的本机。

## 打开与操作

双击仓库根部的 [更新编辑器.cmd](../更新编辑器.cmd)，或在本仓库执行 `npm run release:editor`。只想查看状态可执行 `npm run release:status`。窗口关闭后草稿保留在该工作树的 Git 元数据目录，不进入源码、不上传。

1. **先审查功能代码。** 看当前分支、HEAD、最近版本标签之后的提交（最多 50 条）和未提交文件。功能代码由维护者自行检查和本地提交；守卫没有“一键把全部文件加入发布”的动作。
2. **保存草稿。** 填正式版本（如从 `0.2.0` 到 `0.2.1`）和更新说明。保存不会改包版本、提交代码或接触远端。草稿绑定本地 HEAD 和 `origin` 的推送地址。
3. **准备。** 要求在 `main`、无未提交或未跟踪改动、未处于合并/变基等流程中、目标版本高于当前版本、没有同名本地标签。只写 `package.json`、`client.js` 的版本声明，以及 `docs/releases/v<版本>.md`。不会暂存、提交、推送。
4. **校验。** 检查版本声明与完整文件内容，运行版本一致性、宿主、客户端及守卫自身的隔离测试。测试通过前不能发布；准备或验证后代码变动会阻止沿用旧确认。「返回编辑」仅撤回守卫准备的、仍匹配记录的文件，保留版本和说明草稿；不会覆盖手工改动。
5. **正式发布。** 核对目标仓库、分支、版本和说明，按提示输入完整标签（如 `v0.2.1`）。守卫再次核对已验证内容和远端 `main`，只提交这次准备的三个文件，建注释标签，并请求 Git 用 `--atomic` 一起推送分支与标签。不强推、不改已有的同名标签。成功后再核对远端两个引用；全部吻合才清除草稿。

## 遇到阻拦时

| 提示 | 该怎么做 |
|---|---|
| 工作区不干净、草稿绑定的 HEAD 变了 | 先看变更，自己提交或移出不属于此次的文件；回到编辑阶段重新核对、保存草稿，不要盲目清理工作区。 |
| 有文件在准备后被手动修改 | 先备份个人编辑，再核对版本文件与发布说明。守卫拒绝覆盖或删除与准备快照不符的文件。 |
| 校验未通过 | 看错误末尾的失败用例。返回编辑，修代码并自行提交；重新保存草稿、准备、校验。 |
| 其他窗口更改了草稿 | 刷新状态，核对草稿、HEAD、目标和阶段后再继续。不得拿旧窗口的确认发布另一个候选。 |
| 远端 `main` 已分叉/同名标签冲突 | 停止发布，检查 `git ls-remote` 及提交历史。守卫不会自动合并、强推或删除标签。 |
| 推送失败或结果未确认 | 保留本地发布提交、标签与待推送状态。先查看错误中核实的远端信息，解决网络/权限/策略问题，再次确认同一版本。重试不会创建第二个发布提交。某些服务端隐藏引用时，即便申请了原子推送也可能出现只更新了一个引用；不要依据失败提示假定远端没动，更不要强推回滚。 |
| 提示发布锁存在 | 正常操作会自动释放。若上次异常退出，查看 Git 元数据目录里的 `vig-release.lock`，确认锁内 PID 和对应进程确已退出后才人工处理；不要在操作运行时删除锁。 |

旧的 `tools/push-update.ps1` 不再执行 `git add -A` 或直推。守卫约束的是项目提供的发布入口；本机有 Git 写权限的人仍可绕过它使用原生 Git。若希望所有人都必须经过审批，请另行在托管端配置受保护分支/标签与 CI；本工具不修改仓库托管权限。

## 离线复验

运行 `npm run test:release-guard`。测试使用临时本地 clone/bare 仓库和仅文件传输的 Git 环境，不推送到项目的真实远端。编辑器与守卫不应放入普通工作台的 Web API；维护者可复用 CLI 的 `status`、`save`、`prepare`、`reopen`、`verify`、`publish` 操作（写请求从标准输入读取 JSON）。
